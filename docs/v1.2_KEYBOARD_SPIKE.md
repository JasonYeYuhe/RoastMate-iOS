# v1.2 Custom Keyboard Extension — Feasibility Spike

**Date:** 2026-05-18 · **Status:** spike complete, skeleton built. **DECISION
RESOLVED 2026-05-19 → Option B (re-rank).** The spike materially changed the
risk picture; the user chose to keep the Share Extension as the capture surface
and reallocate the v1.2 spine. See "Recommendation" below for the resolution.

## Why this spike

The next-phase plan made a **Custom Keyboard Extension** the committed v1.2
"native capture moat" spine (Gemini 3.1 Pro's headline idea: generate/rewrite
comebacks in-place inside iMessage/WhatsApp/IG, no unannounced APIs). Before
committing multi-week build effort, this spike pressure-tested feasibility
against iOS keyboard constraints and the existing codebase.

## Hard constraints found

1. **Memory ceiling ≈ 48–60 MB** for a keyboard extension (device-dependent,
   widely documented as a hard ~48 MB on older/again-tightened limits). Apple
   **Foundation Models** on-device LLM cannot run in that budget. → **Inline
   on-device generation is infeasible.** ([Fleksy](https://www.fleksy.com/blog/limitations-of-custom-keyboards-on-ios/), [Apple ExtensibilityPG](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html))
2. **No network without Full Access.** A keyboard is sandboxed with no network
   by default; the cloud Vent/Feral path would require the user grant **Full
   Access** (`RequestsOpenAccess`). Inline cloud generation is therefore
   rejected: it breaks the privacy-led brand, creates the keylogger-trust
   problem, and still can't host crisis-handoff / Pro gating / 5.1.2(i) consent
   (which by codebase precedent — `QuickVentIntent` — must live in the app). ([Apple: configuring open access](https://developer.apple.com/documentation/uikit/configuring-open-access-for-a-custom-keyboard))
3. **App Group access also requires Full Access.** The shared container
   (`group.yyh.roastmate.app`) — our only handoff channel — is blocked for a
   keyboard until the user grants Full Access. So **even a network-free
   capture-and-handoff keyboard needs Full Access** just to pass text to the
   app. *(Confidence: high from Apple's sandbox docs; flagged for on-device
   confirmation before any ship commitment.)*
4. **A keyboard cannot reliably launch its host app.** No public `openURL`
   from `UIInputViewController`. Handoff completes passively (app drains the
   parked text *next time the user opens RoastMate*), not as a live jump.

## Viable architecture (the only coherent one)

**Capture-and-handoff, never inline generation** — exactly mirroring the
deliberate `QuickVentIntent` "open the app, don't generate headlessly"
design (Pro gating + crisis safety + 5.1.2(i) all stay in-app):

- Keyboard reads the current field via `textDocumentProxy`, user taps a
  "Vent about this → RoastMate" key.
- It parks the text in the App-Group suite via the new
  `LaunchRouter.flagCapturedSituation(_:)` (peer of `flagQuickVent`).
- The app drains it (`consumeCapturedSituation()`) on next foreground —
  reuses the existing RootView/RoastGeneratorView Pillar-C drain path;
  pre-fills the situation box; user picks intensity; **unchanged
  SafetyFilter/crisis gate + cloud-consent gate still run in-app.**
- Keyboard does **zero network**. Trust copy becomes: *"the RoastMate
  keyboard never touches the internet — it just hands your rage to the app."*

## How the spike changed the risk picture (honest)

Gemini pitched the keyboard as a frictionless in-place moat. The constraints
demote it to: **a Full-Access-requiring, non-self-launching, capture-only
shortcut** whose end-to-end UX (type → tap key → *manually open RoastMate* →
generate) is only marginally better than the **Share Extension that already
ships**. The "Full Access" ask is also in direct tension with the privacy-led
brand that is the actual moat. Codex's caution against over-relying on any one
capture mechanism applies.

**This is the spike doing its job** — finding, for ~1 day, that the v1.2 spine
is shakier than the plan assumed, *before* spending weeks.

## Recommendation → DECISION (resolved 2026-05-19: Option B)

- **Skeleton built** (compiles, wired, green) so the option is real and a
  future build starts from a foundation — see below.
- **Did NOT auto-commit the multi-week full-keyboard build.** The spike
  changed the premise; per the agreed boundary ("surface decisions that
  materially affect product direction"), the GO/NO-GO was the user's:
  - Option A — proceed: accept Full Access + passive handoff; differentiate
    on "network-free keyboard" privacy framing.
  - **✅ Option B — re-rank (CHOSEN by the user, 2026-05-19):** keep the Share
    Extension as the capture surface, and reallocate the v1.2 spine to the
    next-best moat (**deepen on-device Vent quality / the share-loop**), since
    the keyboard's moat thinned out and its Full-Access cost fights the brand.
    Both advisors' synthesis favored this. The keyboard skeleton (`14f3e6e`)
    **stays committed but dormant** — a real foundation if Option C's loosening
    ever lands; no code is removed.
  - Option C — defer: revisit if a future iOS loosens keyboard App-Group
    access or memory.

## What was built in this spike (committed)

- `LaunchRouter` extended: `flagCapturedSituation` / `pendingCapturedSituation`
  / `consumeCapturedSituation` (Shared/, unit-tested, mirrors quick-vent).
- `RoastMateKeyboard` extension target: `project.yml` block (clone of the
  `RoastMateControls` app-extension pattern), Info.plist
  (`com.apple.keyboard-service`), App-Group entitlements, embedded in the app.
- `KeyboardViewController` minimal **spike skeleton** (next-keyboard button +
  "Vent about this → RoastMate" capture action + a thin insert row) — NOT a
  full QWERTY layout (that is the deferred multi-week scope).
- xcodegen regenerated; app builds with the embedded target; unit suite green.

**Out of scope (the deferred build):** full keyboard layout/locales/autocorrect,
the in-app drain UI for captured text, Full-Access onboarding + privacy copy,
on-device App-Group-without-Full-Access validation on a real device.
