# Track 0.2 — zh-Hans SENDABLE cloud-quality eval

_Run 2026-09-03. Gate for flipping `cloud_sendable_enabled`._
_Raw: `evals/runs/run-0.2-sendable-zh/` and `run-0.2-sendable-zh-run2/`._

## How this was run without opening the path in production

`mode:"roast"` is gated off in prod (`ROAST_MODE_ENABLED=false`). Rather than
flip that on live traffic, the eval ran against
`wrangler dev --remote --var ROAST_MODE_ENABLED:true` — the real Worker code
with real secrets and real models on Cloudflare's edge, reachable only on
localhost. Production was checked before and after and returned
`403 mode_unavailable` throughout.

Harness: `eval-runner` gained `--mode`, `--variants`, `--endpoint`, so this is
repeatable rather than a one-off script.

## Result: 48/48 cells (100%), two independent runs

8 scenarios × {calm, sharp, savage} × zh-Hans × 3 variants.

| | calm | sharp | savage |
|---|---|---|---|
| run 1 (re-graded) | 8/8 | 8/8 | 8/8 |
| run 2 (fresh sample) | 8/8 | 8/8 | 8/8 |

The sendable bar is the **inverse** of the vent bar — vent wants strong words,
sendable wants exactly zero:

- zero profanity — **48/48**
- language match (Han, no kana) — **48/48**
- safety denylist clean — **48/48**
- 3/3 numbered variants parsed — **48/48**
- avg length 256–329 chars for 3 variants; latency 2.5–2.8s

Gate was >85%. Comfortably clear.

## The first grade said 88%, and it was wrong

All three initial "failures" were the checker, not the model. The strong-word
list matches substrings, and **操 is only profane standalone**:

- `少操这份闲心` — "don't trouble yourself"
- `亲自操刀` — idiom, "handle it personally"
- `忘得一干二净` — idiom, "completely"

The first fix (denylist the benign compounds) also failed: 操心 can be split by
an infix, and 干 appears mid-idiom. The benign set is unbounded.

Fixed by **inverting to a profane-construction allowlist** — the verb followed
by a person-object (操你 / 干他 / 操蛋), or standing alone bounded by non-Han.
Probed both directions so the fix narrows rather than silences:

```
操你妈的，这也太离谱了  -> 2      少操这份闲心  -> 0
我他妈受够了            -> 1      忘得一干二净  -> 0
                                  亲自操刀      -> 0
```

**This false positive also affects the historical VENT baselines.** It is
harmless there — it inflates a count that is supposed to be high — but past
vent strong-word numbers are slightly overstated. Noted rather than
retroactively restated.

## Verdict: quality is a GO. The flip is NOT yet safe.

The model quality question this eval was created to answer is settled: the
deployed zh-Hans model produces genuinely sendable output. But two things must
land before `cloud_sendable_enabled` goes true, and neither is about quality.

**1. Client surfaces are not wired.** ~~Three of four~~ **TWO** — corrected
below. Only `RoastGeneratorViewModel` passed `cloudSendableAllowed` into the
engine; `FeatureGenerator` and `ArgumentSimulatorViewModel` did not, so on an
iOS-18 device with no on-device model they would fail rather than reach cloud.

`GenerateRoastIntent` is **deliberately** not wired — its own comment calls it
"an intentional UNMETERED promotional surface: it does not spend wallet
credits". Wiring it would turn a free surface into a cost surface. My first
reading counted it as a bug; it is not.

**RESOLVED** the same day: `Shared/Services/CloudPermission.swift` is now the
single resolution point and all three in-app surfaces call it. Same failure
shape as the M-b roommate-token bug — a multi-step rule living privately inside
one caller, so the second caller silently missed it.

**2. It is a two-key flip.** The client flag ANDs with the Worker's
`ROAST_MODE_ENABLED`, which is separately false. Both must move, and the client
flag also ANDs the 5.1.2(i) consent grant.

## Coverage limits worth stating

- **zh-Hans only.** zh-Hant, ja and en sendable are untested. zh-Hant is the
  higher risk of the three — simplified/traditional character bleed has bitten
  this project before.
- Scenario set is `evals/scenarios/base.json` (8 archetypes), not a broad
  sample.
- Grading is deterministic checks, not human judgement of whether the line
  actually *lands*. Reading run 2's output, quality is good — but that is a
  reader's impression, not a measurement.

## Follow-up: the other three locales (same day)

`--locale zh-Hant,ja,en` × {calm, sharp, savage} = 72 cells.

| locale | clean | verdict |
|---|---|---|
| ja | 24/24 | GO |
| en | 24/24 | GO |
| **zh-Hant** | **18/24 (75%)** | **NO-GO** |

### The zh-Hant check had to be built before it could fail

`checkLanguage` only asks "is this Han?", which Simplified text passes
trivially, and this file previously deferred simplified/traditional bleed to
"per-scenario manual rating" — i.e. it was not being measured. Added
`simplifiedBleed`, counting characters that exist ONLY in Simplified, and
deliberately excluding 里 and 后 (both valid Traditional with different
meanings — 裡 "inside", 後 "after"), which would otherwise be false positives.
Probed both directions before trusting it.

Without it, zh-Hant would have reported **24/24** and been a false GO on the
exact locale flagged as riskiest.

Six cells leaked, one of them writing the **entire response in Simplified**.

### Cause was the prompt, not the model

    zh-Hans: 必须用「简体中文」回复。即使本提示其它部分是英文,你的回复也必须完全使用简体中文。
    zh-Hant: 必須以「繁體中文」回覆。

zh-Hant lacked the reinforcement clause its sibling had, and never forbade
simplified characters at all. `docs/CB_ZH_HANT_AUDIT.md` listed this as
failure mode #1 for the on-device path; it was never fixed on the cloud prompt.

Strengthened with parity reinforcement plus an explicit prohibition naming the
exact characters that leaked, paired with their Traditional forms.

### After the fix — better, still short of the gate

| zh-Hant | before | after |
|---|---|---|
| clean | 18/24 (75%) | **20/24 (83%)** |
| bleed chars total | 38 | **3** |
| worst cell | **33** | **1** |

The structural failure is gone; no response now comes back wholly in the wrong
script. But 83% < 85%, so **zh-Hant sendable remains NO-GO**. Residual: three
single-character bleeds, plus one cell that answered **entirely in English**
(1110 chars) — a dropped instruction, not script bleed, and not fixable by
wording the script rule harder.

### A prediction I got wrong, measured

I expected this to also help the LIVE vent path, since `languageDirective` is
shared. A matched A/B on the same 16 cells (prod's old directive vs the new
one) says otherwise:

| zh-Hant vent | bleed total | worst | langMatch |
|---|---|---|---|
| before | 3 | 1 | 16/16 |
| after | 3 | 1 | 16/16 |

**Identical.** Vent never had a meaningful bleed problem — 3 characters across
16 cells. The failure was specific to the sendable path, where a 3-variant
response is far longer and gives the model more room to drift. The strong-word
average moved 2.8 -> 3.6, but at n=16 against a nondeterministic model that is
noise, not an effect.

So the fix is: **large win on sendable, measured no-regression on vent.**
Deployed (`df0123b3`) on that basis, not on the vent claim I first made.

### A design gap this exposed

`cloud_sendable_enabled` is a **single global flag**. There is no per-locale
gating, so one failing locale blocks the flip for all four — or ships
known-degraded output to zh-Hant users. zh-Hans/ja/en are ready; zh-Hant is
not. That choice does not currently exist.
